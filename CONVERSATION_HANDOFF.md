## PART 1 — Introduction material

### 1.1 Problem statement / motivation

Vasoactive drug titration in the ICU (raising blood pressure in septic shock, or safely lowering it in a hypertensive emergency) is high-stakes, continuous, and currently done by manual observation and manual pump adjustment. Two distinct risks motivate automation:
- **Under-treatment / slow reaction** in septic shock — hypotension causes organ hypoperfusion, and manual titration cadence (minutes) is slower than a computer could react.
- **Over-correction** in hypertensive emergency — correcting blood pressure *too fast* is itself dangerous (it can overwhelm cerebral/coronary/renal autoregulation and cause hypoperfusion injury), so "faster is better" does not even apply here; the correct behaviour requires an actual staged, time-aware safety limit, not just a fast reflex in one direction.

The project's core thesis: a research-grade simulation platform ("digital twin") of both conditions can be used to safely design, tune, and validate both a deterministic control algorithm and supervised AI advisory/early-warning models, entirely before any drug ever needs to be trusted to real physiology — and the same architecture, hardware, and safety philosophy can be shown to generalize to two pharmacologically *opposite* conditions, which is a stronger claim than building one narrow special-purpose system.

### 1.2 Objectives (as actually achieved)

1. Build a literature-grounded mechanistic digital twin of septic-shock physiology under norepinephrine infusion.
2. Build a deterministic, safety-first expert controller that is the sole actuator of pump rate (never the AI).
3. Train supervised ML models that imitate the controller's dosing decisions and independently predict impending deterioration, using only clinically-observable (not simulation-internal) features.
4. Extend the entire architecture to a second, pharmacologically opposite clinical condition (hypertensive emergency / sodium nitroprusside), reusing as much of the existing cardiovascular/physiology engine as possible, to demonstrate the platform is a genuine multi-condition architecture, not a single-purpose script.
5. Design and physically build a real ESP32-S3-controlled syringe-pump prototype, with independent hardware safety layers (E-stop, watchdog, physical limit switches), and demonstrate true hardware-in-the-loop operation (the same computed rate driving both an on-screen simulation and a real stepper motor simultaneously).
6. Build a native desktop monitoring application (not just a browser dashboard) presenting both conditions through one shared UI with a live mode selector.

### 1.3 Explicit non-goals / scope boundaries (important for the report's scope section)

- **This is explicitly a benchtop research/educational prototype, never intended for clinical or patient use.** Real infusion pumps are regulated medical devices subject to standards including IEC 60601-2-24 (the infusion-pump particular safety standard), IEC 62366-1 (usability engineering), ISO 14971 (risk management), and FDA 510(k)/CE clearance — this project makes no such claim. *(Correction, 2026-09-29: an earlier version of this document cited "IEC 62364" here, which is not a medical-device standard at all - it covers abrasion resistance in hydraulic fluid machinery, an unrelated domain; the correct infusion-pump standard is IEC 60601-2-24. That earlier version also claimed this was "explicitly disclaimed... in the firmware source itself" citing these specific standard numbers - checked directly against `pump_firmware.ino` and this is not accurate: the firmware's only disclaimer is a general comment, "This is bench-test firmware for a research/simulation prototype - NOT clinical infusion-pump firmware" (line 97-98), which names no specific standards. Don't attribute the standards list above to the firmware source in your report - it's context for the report's scope section, not a firmware citation.)*
- **The digital twin models the acute IV-titration phase only** (hours), not the multi-day hospital course (real hypertensive-emergency ICU stays average 4-5 days; the simulation's staged safety schedule itself only extends to 48 simulated hours before holding at "normal").
- **Norepinephrine bolus and KVO (Keep Vein Open) modes were deliberately scoped out** of the firmware — norepinephrine is essentially never given as a bolus in real practice, and KVO was simply not prioritized in the time available.
- Demographics **sex/height/BMI** are generated per patient but not wired into any physiological equation (a stated limitation, not an oversight) — only **age** (via a clearance effect) and **weight** (for unit conversion) are actually used.

### 1.4 Why two conditions, and why this specific second drug (useful narrative material)

The second condition was added at the explicit suggestion of the project supervisor, who asked "why not cover both conditions" after seeing the septic-shock work. The key design decision, made deliberately rather than by default, was **which drug** to model for the hypertensive side:

- **Sodium nitroprusside was chosen over nicardipine** specifically because nitroprusside is dosed in mcg/kg/min — the *exact same unit convention* norepinephrine uses — which let the existing mL/hr dose-conversion *formula* be reused unchanged in the Python simulation (both drugs' conversions are `mcg/kg/min → mL/hr` via the same `mass_rate_to_flow_ml_hr()` shape, just with a different concentration constant per drug). Nicardipine, by contrast, is conventionally dosed in mg/hr, which would have required a different formula entirely. *(Correction, 2026-09-29: an earlier version of this document additionally claimed the firmware's keypad weight-based dose-entry mode was reused for nitroprusside "with a different concentration constant" - checked directly against `pump_firmware.ino` and this is false. The firmware defines only one concentration constant, `DRUG_CONCENTRATION_MCG_ML = 16.0` (norepinephrine's), used unconditionally in the keypad's weight-based dose calculation (line 1580) - there is no nitroprusside-specific constant anywhere in the firmware. Entering a nitroprusside dose through that keypad mode as currently written would compute a rate using the wrong concentration (16 vs the correct 200 mcg/mL), i.e. ~12.5x too fast. This matches what Chapter Three already states as a limitation - keep it as a stated limitation, not something this project's firmware actually handles.)*
- The mode is deliberately named **"Hypertensive Emergency Mode"**, not "Hypertension Mode" — ordinary chronic hypertension is never managed with a continuously titrated IV nitroprusside drip; this models the specific, narrow, real clinical scenario (ICU/ED, markedly elevated BP, titrated IV agent) the cited literature actually describes.

### 2.3 General physiology / generic references

- Ringwood JV, Malpas SC — baroreflex/cardiovascular control modeling literature, cited as the structural justification for using a first-order (or first-order-delay) ODE to model the baroreflex (`dHR/dt = k(HRset−HR) − G(MAP−MAPset)`) — this general form is standard across multiple cardiovascular control papers. **Explicitly stated gap**: a single clean, directly-usable numeric gain constant (bpm per mmHg, per simulation tick) was not found in this literature — published baroreflex sensitivity values use inconsistent units (commonly ms/mmHg via RR-interval methods) and vary by study/method — so the specific gain constants (`k`, `G`) used in the model are `[ASSUMPTION]`, tuned for stable simulation behaviour, while the *equation structure itself* is literature-grounded.
- Standard adult haemodynamic reference ranges (CO 4-8 L/min, SV 60-100 mL, SVR 800-1200 dyn·s/cm5, MAP 70-100 mmHg, HR 60-100 bpm, SpO2 95-100%) — consistent across standard ICU/nursing handbook parameter tables and StatPearls physiology articles.
- Standard extracellular-fluid-volume approximation (~20% of body weight) — standard physiology textbook value (Guyton AC, Hall JE, *Guyton and Hall Textbook of Medical Physiology*, 13th ed., Elsevier, 2016 — edition assigned 2026-10-05 as the most commonly cited one for this figure since the edition actually consulted was never logged; confirm against your own copy before submitting), used to derive nitroprusside's per-patient volume of distribution.
- Standard population-PK convention of log-normal inter-individual variability (Ette & Williams, *Pharmacometrics: The Science of Quantitative Pharmacology*) — used for both drugs' clearance variability, since no drug-specific inter-individual variability figure was found in either drug's primary literature.
- Standard "baroreflex resetting in chronic hypertension" physiological concept — used to justify initializing (and, in the newest fix, continuously adapting) the hypertensive patient's baroreflex setpoint toward their own presenting/current MAP rather than the population-normal range.
- Standard KVO (Keep Vein Open) rate convention (1-5 mL/hr), consistent across commercial infusion pump manuals (Alaris, B. Braun, etc.).

## PART 3 — System architecture (Methodology, high level)

```
Patient Generator → Pharmacokinetics (PK) → Pharmacodynamics (PD) → Cardiovascular (CV)
    → Baroreflex/SpO2 → Illness-Recovery/Adaptation → Expert Controller (SOLE actuator)
    → Dataset Generation → AI Model Training (imitation + independent risk) → Dashboard / Native App
    → (optional) Real ESP32 Hardware via Serial, hardware-in-the-loop
```

**The single most important architectural finding of the whole project**: `cardiovascular.py` (`SVR = SVR0×(1+E)`, `SV = SV0×(BV/BV0)`, `CO = HR×SV/1000`, `MAP = CVP+(SVR×CO)/80`) and `physiology.py` (baroreflex HR response, SpO2 heuristic) required **zero modification** to support the second, pharmacologically opposite drug. `compute_svr()`'s `SVR0×(1+E)` formula was never hardcoded to assume the drug effect `E` is positive — a negative `E` (nitroprusside's vasodilation) reduces SVR through the exact same equation a positive `E` (norepinephrine's vasoconstriction) increases it through. Only the two condition-specific layers — pharmacokinetics (drug-specific concentration kinetics) and pharmacodynamics (drug-specific concentration→effect curve) — needed sibling implementations. This is the concrete evidence for the "genuine multi-condition architecture" claim in the objectives.

**Three-tier safety philosophy (applies identically to both conditions, and is the project's central safety argument):**
1. **AI models are advisory only.** The action classifier and flow regressor exist to *imitate* and *display alongside* the controller's decision for comparison/analysis; they never write to `patient.flow_rate`, ever.
2. **The deterministic expert controller is the sole actuator.** It is a hand-written, literature-grounded, unit-testable rule-based control law — not a black box.
3. **Hardware safety is independent of both.** The physical firmware enforces its own absolute rate ceiling, a communication watchdog (auto-stop if no command arrives in time), physical limit switches, and a hardware E-stop — none of which depend on the PC, the simulation, or the AI being correct.

A concrete result that validates tier 1 vs tier 2 (good Discussion material): the hypertensive action classifier, when given enough training data, actually learned to predict the rare cyanide-toxicity-cap event perfectly (1.00 precision/recall/F1) — yet this does **not** argue for letting the AI enforce that safety behavior. The argument for keeping it a hardcoded deterministic controller override is that a research/imitation classifier should never be the safety-enforcement point *even when it happens to test well*, since its correctness was only ever validated on a finite historical dataset, not proven.

**An important asymmetry between the controller and the AI models that Part 7.1 does not make explicit enough on its own, added here (2026-09-29) after report-review found the gap**: the expert controller (both conditions) reads `patient.bp` / `patient.map` directly - the digital twin's **true, noiseless** simulated MAP (`expert_controller.py` line 105: `bp = patient.bp # MAP, mmHg`). The AI models, by contrast, are trained and predict exclusively on `MeasuredMAP` - a separately-computed, Gaussian-noised version (`measured_map = patient.map + N(0, 3.0)`, `generate_dataset.py`) meant to simulate what a real bedside monitor would actually report. Part 7.1's "only information a real bedside monitor/pump could actually observe is used as an AI input feature" describes the AI side correctly, but by omission could read as if the controller operates under the same observability constraint - it does not. This is a real, deliberate design asymmetry (the controller is a mechanistic reference actuator with access to ground truth; the AI models are the ones being asked to do the harder, more realistic job of working from noisy observations only), and it matters for interpreting every AI-vs-controller comparison in Part 8: the AI's task is strictly harder than the controller's by construction, which is part of *why* the imitation-learning accuracy numbers (85-96%, not near-100%) should be read as good performance on a harder task, not as the AI being a worse copy of the controller on the same task.

## PART 4 — Digital twin methodology: equations (both conditions)

### 4.1 Shared/reused equations (both conditions, unmodified)

- **Cardiovascular identities**: `SVR = SVR0 × (1+E)`; `SV = SV0 × (BV/BV0)`; `CO = HR × SV / 1000`; `MAP = CVP + (SVR × CO)/80`.
- **Baroreflex (HR)**: `dHR/dt = k×(HRset − HR) − G×(MAP − MAPset)`, Euler-integrated, k=0.15/min, G=0.30. **Septic side only**, the pressure-deviation term is capped (updated 2026-09-28 - see Part 10.1 items 15/29): ±25 mmHg while MAP is still below `target_bp − TARGET_DEADBAND` (the acute/pre-target phase - deliberately loose, since a strong, fast compensatory HR rise genuinely helps raise MAP via `CO=HR×SV`), tightening to ±10 mmHg once `MAP ≥ target_bp − TARGET_DEADBAND` (at/near target - "at or near target" is defined by this exact one-sided inequality, the same condition used for the illness-recovery clock below). This prevents a rare combination of independently-sampled `hr_set`/`map_set` from producing unrealistic >145 bpm sustained tachycardia, without blunting genuine emergency compensatory response. The hypertensive side deliberately applies **no cap at all** - its own `map_set` continuously drifts toward current MAP (baroreceptor resetting, Part 4.3), which is judged a more physiologically faithful way to bound the reflex over long treatment courses than a hard cap would be.
- **SpO2 heuristic**: two zones (updated 2026-09-28 - see Part 10.1 items 11/30, this was a real bug in the version this document previously described). Declines when MAP is below 65 mmHg (a fixed, drug-agnostic perfusion-adequacy threshold, not tied to whichever target a patient happens to be assigned) minus a 3 mmHg deadband, i.e. below 62 mmHg; recovers (moves toward 100%) at or above 62 mmHg. A deadband is kept only on the lower/decline boundary, to avoid sub-1-mmHg noise flip-flopping right at that one edge - there is no longer a separate "hold steady" zone between two boundaries. SpO2 is clamped to [70, 100] in both twins.

### 4.2 Septic shock / norepinephrine-specific equations

- **PK (one-compartment IV infusion)**: `dCp/dt = R/Vd − ke·Cp`, `ke = CL/Vd`, Euler-integrated. `R` (mcg/min) is derived from the pump's mL/hr flow rate via the cited 16 mcg/mL premix concentration.
- **PD (Emax/Hill model)**: `E = Emax·Cp^γ / (EC50^γ + Cp^γ)`, with `Emax=1.2`, `EC50=6.0 mcg/L`, `γ=1.5` — all `[ASSUMPTION]`, calibrated (not picked blind) against the steady-state plasma concentration range implied by real clinical dosing (typical maintenance 2-4 mcg/min → Cp~0.7-1.3 mcg/L at best-case clearance; typical initial dosing 8-12 mcg/min → Cp~8.9-13.3 mcg/L at worst-case clearance), since Beloeil et al.'s own fitted Emax parameters for this exact drug/population could not be reliably extracted from available sources.
- **Illness recovery (weaning)**: "in target" for starting the recovery clock is the same one-sided condition used by the baroreflex cap above - `MAP ≥ target_bp − TARGET_DEADBAND` (i.e. at or above 62 mmHg for the default 65 mmHg target; there is no upper bound, since MAP naturally drifting *above* target as illness resolves is the desired recovery signature, not something that should pause the clock - only a genuine drop back toward/below the lower bound resets it to zero). Once `time_in_target` exceeds a `ILLNESS_RECOVERY_GRACE_MIN=5.0`-minute grace period, `svr0` (baseline vascular tone) drifts exponentially toward a healthy ceiling `ILLNESS_RECOVERY_SVR0_CEILING_DYN_S_CM5=1050.0` dyn·s/cm5 with time constant `ILLNESS_RECOVERY_TAU_MIN=30.0` minutes (`svr0 += (ceiling − svr0) × (dt/tau)`), tapering drug requirement naturally with **no special-cased weaning logic in the controller** — the existing PD control law tapers flow on its own as `svr0` recovers. Verified directly: SVR0 climbed 479→1031 dyn·s/cm5 over 110 simulated minutes for a representative Severe patient, HR genuinely declined 90.2→72.2 bpm over the same window (not capped or faked — an emergent physiological consequence).

### 4.3 Hypertensive emergency / nitroprusside-specific equations

- **PK**: identical one-compartment structure, drug-specific constants. Nitroprusside's ~2-minute circulatory half-life gives it a somewhat larger `ke` than norepinephrine's, with no special "fast drug" mechanism needed - the standard one-compartment equation produces the onset-speed difference from Vd/clearance alone. *(Corrected 2026-10-04: this previously said ke was "roughly two orders of magnitude larger" - checked directly by simulating both twins and comparing ke=clearance_l_min/vd_l for representative patients, and that number doesn't hold up: ke_NE≈0.14-0.21/min vs ke_SNP≈0.25-0.47/min, a ~1.7-2.7x difference, not 100x. Measuring time-to-90%-of-steady-state-effect from a cold start confirms SNP is still genuinely faster-onset - ~5 min vs ~11-13 min for NE across 3 test patients each per drug - so the qualitative claim holds, just not the "two orders of magnitude" figure. See nitroprusside_pharmacokinetics.py's module docstring for the full correction and the exact numbers.)* Volume of distribution is weight-scaled per patient (`Vd = 0.20 × weight_kg`, using the standard ~20%-of-body-weight extracellular fluid approximation), unlike norepinephrine's fixed population Vd — because the FDA label describes nitroprusside's own distribution volume as tied to extracellular space (i.e., weight-dependent), unlike norepinephrine which Beloeil et al. found NOT weight-dependent.
- **PD**: same Emax/Hill structure, but returns a **negative** effect (`EMAX_ASSUMED=-0.70`, i.e. SVR can fall to 30% of baseline at maximal effect), reflecting vasodilation instead of vasoconstriction. `EC50=20 mcg/L`, `γ=1.5`, calibrated the same steady-state-Cp-range way as the septic side.
- **Staged safety floor (the core clinical safety mechanism, no septic-side equivalent)**: rather than a single fixed target, the "safe MAP" is a three-phase, time-dependent piecewise-linear floor anchored to each patient's own **presenting** MAP:
  - Hour 0-1: floor glides from presenting MAP down to `presenting × (1 − 0.25)` (≤25% reduction).
  - Hour 1-6: floor glides further to the ~160/100-110 mmHg-equivalent MAP band (≈120-127 mmHg, via the standard `MAP = DBP + (SBP−DBP)/3` conversion).
  - Hour 6-48: floor glides the rest of the way to normal MAP range (70 mmHg).
  - Beyond 48h: floor holds at 70 mmHg.
  This floor is a **guardrail the controller must not push MAP below**, not a target to chase directly — "MAP too high" does not mean "correct as fast as possible" in this condition.
- **Baroreceptor resetting** (added late, see Part 8.4 bug history — originally map_set was fixed at the presenting MAP forever; now drifts continuously toward current MAP with a 24-hour time constant, to prevent unbounded reflex tachycardia over long treatment courses while preserving early, clinically-expected acute tachycardia).
- **Illness recovery (vascular tone normalization)** — svr0 drifts toward a normal-tone ceiling (1050 dyn·s/cm5, same numeric target the septic twin's own recovery mechanism uses) once MAP has held at/above the (descending) floor for a grace period, pausing on any breach. Added for the same reason as the septic mechanism — without it, a controller correctly chasing an ever-stricter descending floor against a permanently-fixed vascular resistance must administer an ever-increasing dose forever, with no plateau.
- **Cyanide/thiocyanate toxicity monitor** — a purely deterministic, non-AI safety accounting layer: tracks cumulative administered dose (mcg/kg); flags `cyanide_rate_risk_active` when cumulative dose exceeds 500 mcg/kg AND the current rate exceeds 2 mcg/kg/min (both must hold, per the FDA label's specific rate-dependent-risk wording); flags `cyanide_buffer_exceeded` when cumulative dose exceeds the total 10 mg/kg buffering capacity. The twin only tracks and reports these flags; enforcement (capping or stopping the rate) is the controller's job.

## PART 5 — Patient generation methodology (both conditions)

Both conditions use a shared, unmodified `PatientDemographics` class (age 22-85 uniform, sex, weight 45-120 kg, height 150-195 cm, BMI derived) — demonstrating the generic parts of the architecture are genuinely reusable, not just the physiology equations.

**Septic-shock population**: four severity profiles (Healthy/Mild/Moderate/Severe), weighted 40/30/20/10%. Clearance is derived from a SAPS-II-illness-severity interpolation (citing Beloeil et al.'s two anchor points) further adjusted by an age-related reduction (citing Esler et al.), plus log-normal inter-individual variability. Baseline MAP is sampled directly per profile band (Healthy reuses the normal 70-100 mmHg range; Mild/Moderate/Severe use proportional bands below the 65 mmHg shock threshold — flagged honestly as an undocumented-but-proportional assumption below the cited threshold, since no literature source grades septic shock severity tiers by a specific MAP band, only the SVR citations are per-tier). Cardiac output is then *derived* from the sampled MAP and independently-cited SVR (rather than sampled independently), specifically fixing an earlier discovered bug where independent sampling produced physiologically nonsensical baseline haemodynamics (see Part 10 bug list, item 2).

**Hypertensive population**: four severity profiles (Healthy/Stage2/Urgency/Emergency), weighted 30/30/25/15%. Presenting MAP bands are *derived* from real SBP/DBP clinical staging thresholds (ACC/AHA 2017) via the standard MAP conversion formula. SVR bands are proportionally escalated above normal (flagged honestly as `[ASSUMPTION]`, since — unlike septic shock — there is no equivalent invasive haemodynamic profiling literature for hypertensive-emergency patients specifically; they are rarely instrumented with the arterial/thermodilution catheters septic-shock studies used). Blood volume fraction is held at 1.0 for all profiles (hypertensive emergency is not a volume-depletion state, unlike septic shock). The baroreflex setpoint (`map_set`) is initialized to each patient's own presenting MAP (chronic baroreflex resetting) rather than the population-normal range septic patients use — this single choice is what makes reflex tachycardia emerge naturally as treatment lowers MAP, with zero additional code.

## PART 6 — Expert controller methodology (both conditions)

Both controllers are hand-written, continuous proportional-derivative (PD) rule-based laws computed in mcg/kg/min and converted to mL/hr only at the final step via patient weight — never a black-box model.

**Septic-shock controller** (`expert_controller.py`): continuous PD law drives MAP toward the (clinician-adjustable) target; two hard tiers sit outside the continuous law - (1) an absolute-emergency escalation when `MAP < EMERGENCY_MAP_MMHG=50` (mode="Emergency", full-step increase regardless of target), and (2) a hard-decrease tier when `MAP > target + TARGET_DEADBAND(3) + BIG_OVERSHOOT_MARGIN_MMHG(15)`, i.e. more than 18 mmHg above target (mode="Decrease", full-step decrease). Between these two extremes, the continuous PD law (`step = KP×error + KD×trend`, clamped to ±`MAX_STEP_MCG_KG_MIN`) governs, with `Mode` labeled Maintain/Increase/Decrease per the sign of the resulting step and which side of target MAP sits on. Separately, `SpO2<90` triggers a *label-only* hypoxia overlay applied last (forces `Mode="Emergency"` and prepends a warning to the explanation string) - this never touches `flow`, since dosing more norepinephrine cannot fix a non-shock oxygenation problem, only MAP.

**Hypertensive controller** (`hypertensive_expert_controller.py`) — a genuinely different design, not a copy-paste with signs flipped, because the clinical requirement is genuinely different:
- Tracks the **staged floor**, not a fixed target.
- Uses a **much smaller max step per tick** (`MAX_STEP_MCG_KG_MIN=0.01`, vs the septic side's proportionally-larger convention) — an important, non-obvious finding: an initial step size chosen by direct analogy to the septic controller's "small fraction of max dose" convention caused Urgency/Emergency profiles to overshoot the floor by 19-48 mmHg within the first minute, because nitroprusside's near-instantaneous onset means even a proportionally tiny step produces a large, immediate physiological effect — unlike norepinephrine, where the same convention is safe.
- **Has no fast-ramp-up "Emergency" escalation tier at all** — this is a deliberate, clinically-motivated design difference, not a tuning oversight: the FDA label's own protocol for this drug is "start low, titrate every few minutes," with no stated emergency-escalation exception, unlike norepinephrine where escalating hard during genuine hypotension is standard and correct practice. The high-MAP threshold is instead a **label-only overlay** (mirrors the septic side's SpO2 overlay pattern) — it flags the state for review but never itself changes the flow.
- **Has a genuine safety-critical override the septic controller has no equivalent of**: the cyanide toxicity monitor can force a hard rate cap (`Toxicity-Cap` mode) or a full stop (`Toxicity-Stop` mode), overriding whatever the continuous PD law would otherwise compute.

Re-tested after the step-size fix: all three treated profiles track the staged floor within ~1 mmHg for a full simulated hour without ever breaching it (this was the validation baseline *before* the later multi-hour recovery-mechanism bug was found — see Part 10.4).

## PART 7 — AI methodology (both conditions)

### 7.1 Feature-selection philosophy (both conditions)

Only information a real bedside monitor/pump could actually observe is used as an AI input feature - specifically the noised `MeasuredMAP`/`MeasuredHR`/`MeasuredSpO2` family, never the twin's true `MAP`/`HR`/`SpO2`. This is a real asymmetry with the controller, which *does* read true MAP directly - see Part 3's "important asymmetry" note for the full explanation and why it matters for interpreting Part 8's results. Internal simulation ground truth (SVR, cardiac output, plasma drug concentration, drug effect, clinical severity Profile/SAPS-II) is retained *only* as hidden diagnostic ground truth, explicitly excluded from training features — because it would otherwise be close to an answer key (leakage-adjacent), not a real deployable signal. For the hypertensive side, cumulative administered dose and the two deterministic cyanide flags *are* included as legitimate features, since — unlike internal physiology — a real pump can trivially compute how much drug it has already delivered.

### 7.2 The two independent prediction tasks (both conditions)

1. **Imitation-learning models** (action classifier + flow-rate regressor): learn to reproduce the expert controller's own decision from observable state. Trained on the controller's actual chosen action/rate at each tick.
2. **Independent risk/early-warning model**: a genuinely different, forward-looking task, built by looking ahead into each simulated patient's *own future* trajectory (impossible for the controller itself to know) — septic side: `WillDeteriorate` (MAP will fall below an emergency threshold or SpO2 below 90 within a lookahead window); hypertensive side: `WillBreachFloor` (MAP will fall below its own future floor, OR the cyanide rate-risk flag will trip, within the same lookahead window).

### 7.3 Dataset construction and train/validation/test methodology

**Patient-level splitting (not row-level) is essential and was applied on both sides**: each simulated patient contributes hundreds to thousands of highly autocorrelated per-second rows. Splitting *rows* randomly would let a model see part of a patient's trajectory during training and be "tested" on another part of the *same* patient — genuine data leakage, since the model would have partial knowledge of that exact patient's response curve. The fix used throughout: every patient is assigned, via an independent seeded random-number stream, to exactly one of train/validation/test — entire trajectories move together.

- **Septic side**: an explicit **210/30/60 patient split** (train/validation/test, of 300 total) — reworked 2026-09-27 from an earlier 250/60 split that had no formal validation set. Test was deliberately kept at 60 patients for continuity with earlier-reported figures; the 30-patient validation split was carved out of what used to be a larger training set. A leakage check (confirmed empty set) was run and passed.
- **Hypertensive side**: an explicit **700/100/200 patient split** (train/validation/test) — this is the standard "80% development (further split 700/100 into train/validation), 20% held-out test" methodology restated as 70/10/20-of-total, not the sometimes-misquoted 80/10/10. A leakage check (confirmed empty set — no `(seed, patient_id)` pair appears in more than one split) was run and passed.

Both clinical modes now use the same rigor. Both were originally reworked from an earlier, less rigorous approach — the hypertensive side first, the septic side after the user asked "don't you think not having a validation set for the norepinephrine side is bad?" during report-writing review.

**Hyperparameter selection methodology (now identical on both sides)**: a small `max_depth` grid is fit — on a training subsample for the hypertensive side only, given its much larger row count; on the full training set for the septic side — with each candidate scored on the **validation** set (accuracy for classifiers, MAE for regressors, ROC-AUC for the risk models), and only the winning configuration is ever evaluated against the held-out **test** set — test is touched exactly once, for the final reported number, per model. The final model for each task is then refit on combined train+validation at the full `n_estimators=500` before that one test evaluation. *(Correction, 2026-09-29: an earlier version of this paragraph stated the septic regressor's grid as `[10, 15, 20]` - that was wrong and contradicted Part 8.1's own reported result of `max_depth=6` selected, which isn't even in that grid. The septic regressor actually uses the same shallower grid as the hypertensive regressor, for the same reason - see Part 7.4.)* The grids actually used: `[10, 15, 20]` for both action classifiers and both risk models; `[6, 10, 14]` for **both** flow regressors (deliberately shallower than the classifier/risk-model grid on both sides, since a delta target - see Part 7.4 - is a lower-cardinality, more compressible signal that doesn't need or benefit from the same depth budget).

**Flow regressor - trivial-regression issue found and fixed, same day**: the first retrain under the new validation methodology selected `max_depth=10` and reported test R²=1.000, MAE=0.180 mL/hr, but feature importance showed `FlowRate` alone at 99.9% — the model was essentially copying its own input, exactly the trivial-regression problem the hypertensive side had already fixed by predicting a *delta* target instead of the absolute flow value. Fixed identically here: `train_ai.py` now predicts `RecommendedFlow - FlowRate` (see its module docstring "Why delta, not absolute flow", copied from `train_hypertensive_ai.py`'s identical rationale), and `native_app.py`'s septic `SimEngine.step()` (~line 392) was updated to reconstruct the absolute AI-suggested flow as `patient.flow_rate + predicted_delta`, clamped to `[0, MAX_FLOW_ML_HR]` — the exact pattern the hypertensive `HypertensiveSimEngine` already used (added earlier this session to fix the negative-AI-flow display bug). Both clinical modes' flow regressors now use the same honest delta-target methodology - no open caveats remain on this point.

**Baroreflex HR fix, later the same day**: user reported HR climbing almost in lockstep with MAP's own recovery rate in a live septic-mode session, reaching ~130 bpm for a Severe-profile patient right around when MAP first reached target, with SpO2 also declining continuously at a slower comparable rate. Root cause found in `digital_twin.py`: `constants.py` already documented that unbounded baroreflex deviation had previously produced simulated HR above 145 bpm in ~20% of a 60-patient sweep, and a cap (`BAROREFLEX_MAX_DEVIATION_MMHG=10`) was added specifically to fix that - but the cap was only ever wired in for the "MAP already at/near target" case. During the acute pre-target phase, `max_deviation_mmhg` was still passed as `None` (fully uncapped), so an unlucky independent draw of `hr_set`/`map_set` (both sampled from normal reference ranges, occasionally both landing near the high end) could drive HR past 130 bpm within the first couple of simulated minutes, before MAP had caught up - reproduced directly: a test patient with `hr_set=97.7`, `map_set=97.0` hit HR=126.7 exactly at MAP's target-crossing. Fixed with a two-tier cap (`digital_twin.py`, ~line 202): a new `BAROREFLEX_MAX_DEVIATION_ACUTE_MMHG=25` during the acute/pre-target phase (deliberately looser than the near-target cap, since HR genuinely contributes to raising MAP via `compute_cardiac_output` and shouldn't be over-constrained during a genuine emergency), tightening to the existing `BAROREFLEX_MAX_DEVIATION_MMHG=10` once at/near target. Verified on the same worst-case patient: HR at target-crossing dropped from 126.7 to 114.9 bpm and stopped climbing past that point. At the time, `update_spo2`'s continued decline was assessed as expected/not-a-bug for the genuinely-refractory case (pump maxed at 190 mL/hr, MAP never reaches target, SpO2 correctly stuck at the 70% floor) - that assessment was correct as far as it went, but missed a SEPARATE freeze case, found and fixed the next day (below). Because the HR fix changes how `MeasuredHR` is generated, the dataset was regenerated and all three models retrained a second time.

**SpO2 recovery fix, 2026-09-28 (next day)**: user reported SpO2 freezing at 89.4% indefinitely even after MAP had stabilized. Root cause in `physiology.py`'s `update_spo2` (shared by both clinical modes): a 3-way split - decline below 62 mmHg, recover above 68 mmHg, hold perfectly STEADY in between (62-68 mmHg). That steady band is exactly the septic clinical target zone (65±`TARGET_DEADBAND`=3) that `expert_controller.py` holds MAP in once treatment succeeds - so a SUCCESSFULLY treated patient got SpO2 permanently frozen at whatever value it held when it entered that band, only resuming recovery if MAP later drifted above 68 via the separate, much slower illness-recovery mechanism. Reproduced directly: a test patient held at MAP=65.0-67.9 mmHg for 900+ simulated seconds had SpO2 frozen at 87.73% the entire time. Fixed by collapsing the 3-way split to a 2-way one (`physiology.py`, `update_spo2`) - reaching or exceeding the perfusion threshold (keeping a deadband only on the lower/decline side, to avoid flicker right at that boundary) now starts recovery immediately. Re-verified on the same patient: SpO2 reaches 100% within seconds of crossing into target instead of freezing. Shared with the hypertensive twin, but not regenerated there - hypertensive patients rarely linger in the narrow 62-68 mmHg band (they present far above it) per that engine's own code comments. Septic dataset regenerated and all three models retrained a third time.

**Septic-side results, final (real numbers, current as of the retrain following all three fixes - validation-set methodology, delta-target regressor, baroreflex HR cap, and the SpO2 recovery fix - supersedes all numbers reported earlier this week)**: action classifier `max_depth=10` selected, test accuracy 86.7% (macro F1 0.84; per-profile: Healthy 90.4%, Mild 86.9%, Moderate 81.3%, Severe 82.3%); flow regressor (delta target) `max_depth=6` selected, delta R²=0.762, delta MAE=0.1467 mL/hr — the honest, headline figure, since it's scored against a real learned signal, not against a value the model can trivially copy from its own input (see Part 7.4); the reconstructed absolute-flow figure (R²=0.9999, MAE=0.1467 mL/hr) is a secondary, clinically-readable derived view, not the metric to lead with, because it is dominated by the current-flow input rather than by what the model actually learned. Risk model (`WillDeteriorate`) `max_depth=20` selected, test accuracy 99.7%, precision 0.938, recall 0.961, ROC-AUC >0.999 (raw value 0.9998 - reported as ">0.999" rather than the rounded "1.000" a 3-decimal display would show, since the model is not literally a perfect classifier and stating it as such would overclaim). Positive class rate (`WillDeteriorate`) has dropped across each successive retrain (9.0%→8.8%→7.5%→2.9% train-side over the session) as the physiology fixes make treatment succeed more completely - a real, physiology-driven shift, not noise or a data problem.

**Realistic titration-lag injection (a deliberate, documented methodological choice)**: an early version of the hypertensive dataset produced **zero** `WillBreachFloor` positive examples, because the controller was specifically tuned to never breach the floor — meaning there was nothing for a risk model to learn to anticipate. This was fixed not by weakening the controller, but by giving ~30% of *simulated* patients a randomized response delay (30-180 seconds) representing realistic human/manual titration lag, reflecting the fact that real bedside titration is never instantaneous — this genuinely produced real near-miss and breach events (1.6-2.2% positive rate, occurring only in the lagged subgroup, only in the Urgency/Emergency profiles — a clean, explainable, non-arbitrary causal story). Two simpler alternatives were tried first and found not to work: delay alone (no effect, since the controller's proportional term naturally tapers its own step near the floor regardless of ceiling), and just raising the step-size ceiling for that subgroup (also no effect, same reason). Only reintroducing a specific "floor-blind" ramp behaviour (deliberately similar to an earlier, removed controller behaviour) for the lagged subgroup actually produced breach events. **The imitation-learning labels (action/flow) are completely unaffected by this — they always reflect the real controller's ideal decision, never the injected imperfect policy's output.**

### 7.4 Model architecture and a critical methodological correction (the delta-regression fix)

All six models (three per condition) are `RandomForestClassifier`/`RandomForestRegressor` (scikit-learn), 500 trees for final models, `class_weight="balanced"` for the imbalanced classification tasks.

**A significant methodological finding, worth its own Discussion paragraph**: an early version of the hypertensive flow regressor predicted the *absolute* recommended flow rate directly, and scored a seemingly excellent R²=1.000, MAE=0.019 mL/hr. Feature-importance analysis revealed this was almost entirely explained (99.999% importance) by the current flow rate itself — because the controller only moves the rate by a tiny amount per tick, "predict output ≈ current input" is already nearly exactly correct, without the model needing to learn anything about the underlying physiological decision logic. This also produced an impractical 7.46 GB model file (deep trees memorizing near-continuous, near-identical target values). The methodological fix: retarget the regression at the **delta** (`FlowDelta = RecommendedFlow − FlowRate`) instead of the absolute value, with a shallower depth search grid — this removed the trivial-copy shortcut entirely, produced a genuinely interpretable feature-importance profile, and shrank the model to 200.6 MB. The absolute flow prediction (useful for a clinically-readable display number) is still reported, reconstructed as `FlowRate + predicted_delta`, but is no longer what the model is trained or selected against.

### 7.5 Two methodological limitations worth stating honestly in the report

1. **Adjustable decision threshold considered and explicitly declined**: lowering the risk model's classification threshold to catch more true positive breach events would necessarily also increase false alarms — a hard, unavoidable precision/recall tradeoff, not something threshold-tuning can escape. Given the well-documented ICU "alarm fatigue" problem (excessive false alarms cause clinicians to start ignoring alerts, which then fail exactly when correct), the default threshold was deliberately kept, prioritizing sustained clinician trust in the alert over marginally higher sensitivity.
2. **AUC vs. recall as a selection criterion**: hyperparameter selection used validation ROC-AUC, but during the search phase, recall at the default 0.5 threshold actually *decreased* as depth (and AUC) increased (96.5%→78.6%→76.4%) — AUC measures ranking quality across all thresholds, not behavior at the one specific cutoff a deployed system uses. The final model (refit on substantially more data than the search-phase candidates) still achieved a strong 91.7% test recall, so this didn't harm the actual result, but a recall- or F1-oriented selection criterion would arguably have been more clinically appropriate for a safety-alerting model than AUC.

Documented in the firmware source specifically so this isn't re-investigated in a future session.
- **Volumetric (VTBI) accuracy**: commanded a Rate+VTBI run of 10.00 mL at 190 mL/hr (measured from the syringe's own 0 mL graduation mark, positioned away from the physical end-of-travel to rule out the limit switch as a confound). Firmware's own internal tracking reported delivery complete at a wall-clock time (189.53 s) matching the computed expectation (189.47 s) almost exactly — confirming the firmware's rate/time/volume accounting logic is correct. **Real physical output measured on the syringe's own graduation was ~9.8 mL — a ~2% shortfall**, most likely attributable to graduation-reading precision and/or small real-world bore-diameter/lead-screw-pitch/backlash tolerance (a wrong microstepping-mode assumption would produce an error off by an integer multiple — 2x/4x/8x — not a smooth 2%). Left uncorrected by explicit user decision, rather than encoding a single-measurement fudge factor; flagged as revisitable only if repeated trials show a *consistent* (not noisy) shortfall.
- **Autonomous (hardware-in-the-loop) mode**: confirmed working fully end-to-end — a simulated patient's `expert_controller`-computed rate was streamed over serial to the real ESP32, which correctly clamped/applied it and echoed confirmation back, observed through a complete Emergency→Decrease→Maintain control cycle with correct clamping at the pump's own 190 mL/hr maximum and 0 mL/hr minimum.
- **Safety systems confirmed working**: driver starts disabled at every boot; E-stop immediately disables the driver and latches until an explicit reset; a communication watchdog auto-stops the pump if no rate command arrives within 3 seconds (bypassed correctly only when a rate was set manually via the keypad, since there's no PC to "go quiet" in that scenario); physical limit switches block/stop motion at each end of physical travel.

### 8.4 The recovery-mechanism bug: found via real extended usage, not automated testing (strong methodology/Discussion material)

After the hypertensive dashboard mode was built and passed all automated tests (a 200-tick smoke test, a full-hour controller validation), the user ran the actual live dashboard for several real hours and reported the flow rate climbing toward 80 mL/hr and heart rate reaching 163 bpm, both still rising with no sign of plateauing. Root cause: two physiological mechanisms present on the septic-shock side had no hypertensive-side equivalent —
1. Vascular tone (`svr0`) was a fixed constant for the entire simulation, while the staged safety floor keeps descending for up to 48 hours regardless — so the controller had to administer an ever-increasing dose forever just to keep pace against a resistance that never improved on its own.
2. The baroreflex setpoint (`map_set`) was initialized once to the presenting MAP and never updated, so as treatment pushed real MAP down over many hours, the pressure-deviation gap driving reflex tachycardia only ever grew, with no physiological limit.

Both were fixed by adding genuine ongoing physiological mechanisms (vascular-tone recovery once safely controlled for a grace period; continuous, slow baroreceptor-resetting toward current MAP), mirroring — but not copying — the existing septic-side illness-recovery mechanism. **Verified via a 20-simulated-hour worst-case (Emergency profile) run**: flow plateaued at 36 mL/hr instead of climbing toward the maximum, `svr0` converged from 2151→1206 dyn·s/cm5 (toward the 1050 normal-tone ceiling), `map_set` drifted from 170.5→141.7 mmHg (tracking the falling MAP), and HR peaked around 157 bpm before turning around and declining to 147 bpm by hour 20 — still elevated (real baroreceptor resetting genuinely takes about this long) but now bounded and improving rather than runaway. This same extended-run test also caught and led to the fix of a genuinely separate cosmetic bug: the AI's reconstructed absolute flow suggestion could go negative (`-62.5 mL/hr`, physically meaningless) right after a large real rate correction, since the delta-reconstruction (`FlowRate + predicted_delta`) was not being clamped to a valid range — fixed with `np.clip(..., 0, max_flow)`, re-verified against the exact scenario that broke it.

**This episode is strong material for a Methodology/Discussion point about testing strategy**: short validation runs (the original controller check was "a full simulated hour") did not and could not surface either of these bugs, because the failure mode only manifests at the timescale the staged safety schedule itself spans (up to 48 hours). The project's own documented lesson: deliberately test at the full timescale a safety mechanism is designed to operate over, not just a short smoke-test window.

## PART 9 — Discussion / Limitations (comprehensive, honest)

- **Volumetric accuracy**: ~2% shortfall on the physical hardware, accepted rather than corrected without further repeated-trial evidence of a systematic (not noisy) bias.
- **Scope boundary**: the digital twin models the acute IV-titration phase (hours); real hypertensive-emergency hospital courses run 4-5 days on average, with the transition to oral antihypertensives (not modeled at all) being the dominant driver of that longer timescale, not drug pharmacology itself.
- **Firmware scope**: Bolus and KVO modes were deliberately not built for norepinephrine (bolus dosing of this drug is essentially never done clinically; KVO was simply deprioritized under time constraints), and a unified "delivery engine" consolidation across all manual programs was proposed but not completed.
- **Risk-model blind spot**: 0% recall for the rare, low-severity ("Healthy") population's breach events — argued above to be a fundamentally noise-dominated, likely-unlearnable edge case rather than a fixable modeling gap, but it is a real, stated blind spot.
- **Deliberately undefeated tradeoff**: the alarm-fatigue-vs-sensitivity threshold decision cannot be "solved," only chosen — the project explicitly chose fewer false alarms over marginally higher sensitivity, and this should be stated as a values-based design decision, not an oversight.
- **Demographic features not fully utilized**: sex, height, and BMI are generated per simulated patient but never wired into any equation — stated explicitly as a limitation rather than silently ignored.
- **Provisional/unvalidated controller gains**: both controllers' proportional/derivative gain constants and max-step sizes are flagged in the source as provisional, pending the kind of broader seeded-population sweep verification the septic controller's own derivative gain historically received (see Part 10.1, item 10) — the hypertensive controller has not yet received an equivalent broad sweep.
- **AI toxicity-classification finding reframes, rather than removes, the justification for the deterministic safety override**: since the AI classifier *can* learn to predict the cyanide-cap event essentially perfectly given enough data, the argument for keeping this a hardcoded controller override is not "the AI is incapable" but "a research classifier's historical test performance is not the same guarantee a safety-critical enforcement mechanism requires."
- **Methodology parity between the two clinical modes was reached only in a late rework, not designed in from the start**: the hypertensive side was built second but received the more rigorous train/validation/test split, delta-target regression, and validation-based hyperparameter selection first; the septic side initially shipped with a simpler 250/60 split, fixed hyperparameters, and an absolute-value flow regressor that (once checked) showed the identical trivial-copy defect the hypertensive side had already found and fixed. Both sides now use the same methodology (Part 7.3-7.4). Worth stating honestly as a limitation of the development process itself: consistency across near-identical subsystems should ideally be verified proactively, not discovered by a report-writing review question.
- **Two further physiology bugs (baroreflex HR, SpO2 recovery - Part 10.1 items 29-30) were found only through extended real dashboard usage, not automated testing**, echoing the same lesson as the hypertensive recovery-mechanism bug in Part 8.4: short/automated validation runs did not surface either issue, because both only manifest once a patient's trajectory actually holds near the clinical target for an extended stretch - exactly the "successfully treated" scenario a short smoke test is least likely to sustain long enough to observe.

## PART 10 — Bug/debugging history (strong evidence of engineering rigor — useful for a Methodology "verification and validation" subsection or a Discussion point on testing practice)

### 10.1 Septic-shock phase (pure software, earlier in the project)

1. Constructor signature drift between two versions of the digital twin — fixed.
2. **MAP0/CO0 independent-sampling bug**: sampling cardiac output and MAP independently (rather than deriving one from the other and the cited SVR) let Healthy baseline MAP range 50-122 mmHg across a 500-patient seeded sweep — clinically nonsensical for a "Healthy" label. Fixed by sampling MAP directly per profile and *deriving* CO from it and the cited SVR.
3. **KVO-floor bug**: Healthy patients infused continuously because the minimum flow rate defaulted to the KVO (Keep Vein Open) rate rather than zero — fixed.
4. **Zero-variance TargetBP bug**: after adding an adjustable MAP target, the feature had zero variance in training data (every patient used the same default), so the AI could learn nothing about it — fixed by randomizing target per patient during dataset generation.
5. **Emergency/hypoxia dosing bug** (two iterations): flow stayed inappropriately high after MAP reached target; a first fix caused rate chattering (oscillating 0↔190 mL/hr); final fix uses one absolute emergency threshold plus a continuous PD law everywhere else, with SpO2<90 only overriding the *displayed mode label*, never the actual flow rate. Verified zero chattering afterward.
6. Garbled risk-score chart from a charting-library auto-scale quirk — fixed with a fixed [0,1] axis domain.
7. A manual edit accidentally deleted a needed constant from `constants.py` — restored.
8. A `PermissionError` writing a CSV that was open in Excel — closed the file, reran.
9. Patient age was stored as a decimal from `rng.uniform` instead of a whole year from `rng.randint` — fixed, full pipeline re-run.
10. **Controller overshoot bug, root-caused via direct measurement**: the derivative gain (`KD`) had been inherited unchanged from an earlier, coarser control-interval version of the controller; at the current per-second tick rate, the measured trend term was too small for the anticipatory term to matter, letting the controller push dose right up to the boundary before correcting (measured 6-8 mmHg peak overshoot). Retuning `KD` (0.025→0.15) cut this to ~0-1 mmHg with zero new chattering. Two adjacent phenomena investigated during the same pass were confirmed to be *correct behaviour, not bugs*: (a) some Healthy/Mild patients plateau *above* target permanently because their own baroreflex-driven MAP already exceeds target at zero drug (norepinephrine can only raise MAP, never lower it); (b) one Severe patient plateaus below target even at maximum flow, correctly representing the real, recognized ICU phenomenon of **catecholamine-refractory shock**.
11. **SpO2 knife-edge bug (first fix - later found incomplete, see item 30)**: a hard `MAP<65` cutoff with zero tolerance meant a patient settling at MAP 64.97 (clinically indistinguishable from, and within the controller's own deadband of, 65) could get permanently stuck ratcheting SpO2 toward its floor from sub-1-mmHg numerical noise alone. Fixed at the time with a 3 mmHg dead-zone and a three-way decline/hold/recover branch - this fixed the noise-flicker problem but, unnoticed until item 30, introduced a *different*, larger freeze bug of its own.
12. **Investigated and found to be a genuine missing mechanism, not a bug**: HR does mathematically converge (verified to ~92 bpm by ~45 simulated minutes for a representative patient), just slower than any short demo window, *and* it converges to an elevated value because the baroreflex defends each patient's own individual "normal" setpoint (70-100 mmHg), not the clinical 65 mmHg treatment target — a real, clinically accurate tension (real ICU patients held at MAP 65 do stay somewhat tachycardic). The actual gap found: there was no illness-recovery mechanism at all — `svr0` was a fixed constant forever, so nothing ever weaned. This directly motivated building the illness-recovery mechanism described in Part 4.2.
13. A UI beep timer reset itself on every tiny HR fluctuation (nearly every tick), preventing it from ever actually sounding — fixed to only restart on a meaningful (>25ms) interval change or a normal/critical tone switch.
14. Native desktop app tab content had no scroll container and was simply crushed by the layout rather than scrolling on a smaller window — fixed with `QScrollArea` wrapping.
15. **Baroreflex could produce sustained HR >145 bpm, found via a 60-patient seeded sweep (first fix - later found incomplete, see item 29)**: since `hr_set` and `map_set` are sampled independently per patient, an occasional combination (both landing near the high end) compounded into unrealistic sustained tachycardia (peak 149 bpm; 12/60 patients exceeded 110 bpm over a 2-hour sweep) purely from the raw, uncapped pressure-deviation term. Fixed at the time in two iterations: a flat 10 mmHg saturation cap reduced the worst case but *also measurably blunted* genuine emergency compensatory tachycardia (a real regression, caught by comparing Emergency-class training-data prevalence before/after); refined so the cap **only engaged once MAP was already at/near target**, preserving the full, uncapped response during genuine hypotension. This was verified as adequate at the time via direct A/B simulation on identical seeded patients (worst-case sustained HR bounded to ~112-127 bpm) - but "uncapped during the acute phase" turned out to still be a live problem in practice, found later via real dashboard usage (item 29).
16. **A deliberate attempt to fix weak Increase-class AI recall — failed cleanly, and was reverted.** See Part 8.1 — a legitimate negative result, not hidden.

### 10.2 Firmware/hardware phase

17. GPIO19/GPIO20 pin conflict — these are the ESP32-S3's native-USB D-/D+ lines on this specific board; assigning STEP/EN there caused simultaneous "motor does nothing" and "shows not connected" symptoms. Fixed by moving to GPIO2/GPIO42.
18. A4988 motor driver miswiring (VDD momentarily connected to the negative terminal) — real hardware-damage risk, resolved once the actual root cause (missing common ground between the 3.3V logic domain and the 12V motor domain) was found and fixed — this single fix made the whole system work.
19. Battery voltage reading ~12% too low under high-voltage ADC nonlinearity — fixed by switching from `analogRead()` to `analogReadMilliVolts()`.
20. Battery reading noise/instability — fixed with an exponential moving average.
21. **A long-standing intermittent multi-second keypad-transition freeze, root-caused after four earlier fix attempts failed**: the actual cause was the ESP32-S3's native USB CDC blocking `Serial.print()`/`println()` calls when the USB cable is physically connected but no host application has actually opened the port (e.g. Serial Monitor closed) — the internal transmit buffer fills and a blocking write then waits forever for a reader that never comes. Fixed with a single `Serial.setTxTimeoutMs(0)` call, making writes non-blocking. Earlier hypotheses (keypad-library repeat-firing, a blocking buzzer call) were reasonable but wrong, and their fixes — while harmless — did not resolve the actual issue.
22. A real display bug: the LCD helper functions never clamped output to the physical display's actual 16-column width, so overflow text could write into display memory that maps onto the *wrong physical row* on real HD44780-style 16x4 addressing — not merely a harmless cosmetic cut-off. Fixed centrally with a hard 16-character clamp inside the shared display helpers.
23. Motor spun the wrong direction (anticlockwise/pulling instead of clockwise/pushing) once mechanically coupled; the firmware-level fix (inverting the DIR pin's logical meaning) was tested in **both** directions and had **zero effect on actual rotation either way**, proving the DIR signal was not the actual controlling factor for this specific board/wiring. Root cause instead resolved at the hardware level, by physically swapping the two leads of one motor coil pair.
24. A stray leftover character (`return max(cp_new, 0.0)n`) had turned `pharmacokinetics.py` into a Python syntax error, which would have silently broken the *entire* existing septic-shock pipeline the moment anything tried to import it (a leaf dependency of nearly everything) — found and fixed; cause unknown (possibly an external edit between sessions).
25. **Stale packaged build confusion, twice**: on two separate occasions, the user reported "the changes aren't showing up" after double-clicking the packaged `.exe`, when in fact the `.exe` predated the source changes by days to weeks (PyInstaller does not auto-rebuild). Diagnosed both times by comparing file timestamps; fixed by rebuilding via `python -m PyInstaller SmartInfusionAI.spec --noconfirm`. Established as a standing check: always compare exe-vs-source timestamps before debugging a "missing feature" report on the packaged build.
26. **RandomForest training-time catastrophe**: fitting the AI models on the *full* un-subsampled hypertensive training set (2.5-5 million rows) was empirically found to be catastrophically slow — a single 150-tree fit once ran over 5 hours without finishing. Root cause: each simulated patient contributes thousands of highly autocorrelated consecutive one-second rows, giving a tree-based model very little additional signal per extra row seen. Fixed by subsampling the *training* data only (validation/test always stay full-size, since that's what honest evaluation numbers come from) to a fixed target row count, re-derived from the actual dataset size each run so it stays fast regardless of future duration changes.
27. **A single-row-prediction performance bug in the live dashboard, found via the same extended-usage testing described in Part 8.4**: the trained models were loaded with their training-time `n_jobs=-1` setting still attached, meaning every single real-time tick's prediction was needlessly spawning/coordinating parallel worker *processes* to predict just one row — pure overhead with no parallel work to actually split up, and also the root cause of a flood of an unrelated joblib warning that a plain Python `warnings.filterwarnings()` call could not suppress (because those workers are separate OS processes with independent warnings state). Fixed by forcibly setting `model.n_jobs = 1` immediately after loading, specifically for the live-prediction path (the training scripts still correctly use `n_jobs=-1` for fitting, where parallelism is genuinely useful).

### 10.3 Septic-shock methodology/physiology rework, 2026-09-27/28 (report-writing review phase)

These three fixes were prompted by report-writing review questions rather than automated testing or a fresh feature build - included here because they are genuine engineering findings (two of them are real bugs with concrete before/after numbers), not just documentation cleanup.

28. **No validation split on the septic side, unlike the hypertensive side**: the septic dataset used a 250/60 train/test split with fixed, untuned hyperparameters (`max_depth=15` by convention), while the hypertensive side already had a proper 700/100/200 validation-based methodology. Raised by the user during report review ("don't you think not having a validation set for the norepinephrine side is bad?"). Fixed by reworking `generate_dataset.py`/`train_ai.py`/`train_risk_model.py` to an explicit 210/30/60 split (of 300 total, preserving the pre-existing 60-patient test set for continuity) with validation-based `max_depth` selection, mirroring the hypertensive side exactly - see Part 7.3. This retrain also surfaced a second, independent issue (item 29's flow-regressor trivial-copy problem, same trivial-regression signature the hypertensive side had already found and fixed - see Part 7.4), fixed in the same pass.
29. **Baroreflex acute-phase HR spike (supersedes item 15's "only near target" cap)**: user reported live-session HR climbing almost in lockstep with MAP's recovery rate, reaching ~130 bpm for a Severe-profile patient right as MAP first reached target. Root cause: item 15's cap was only ever wired in for the "MAP already at/near target" case; during the acute pre-target phase `max_deviation_mmhg` was still passed as `None` (fully uncapped) - so an unlucky independent draw of `hr_set`/`map_set` (both sampled from normal reference ranges, occasionally both landing near the high end) could drive HR past 130 bpm within the first couple of simulated minutes, before MAP had caught up. Reproduced directly: a test patient with `hr_set=97.7`, `map_set=97.0` hit HR=126.7 exactly at MAP's target-crossing. Fixed with a two-tier cap: a new, looser `BAROREFLEX_MAX_DEVIATION_ACUTE_MMHG=25` during the acute/pre-target phase (still allows a strong, fast compensatory response - HR genuinely helps raise MAP via `compute_cardiac_output`), tightening to the original `BAROREFLEX_MAX_DEVIATION_MMHG=10` once at/near target. Verified on the same worst-case patient: HR at target-crossing dropped from 126.7 to 114.9 bpm and stopped climbing past that point.
30. **SpO2 freeze-at-target bug (supersedes item 11's three-way branch)**: the very next day, user reported SpO2 freezing at 89.4% indefinitely even after MAP had stabilized. Root cause: item 11's fix introduced a 3-way split in `update_spo2` - decline below 62 mmHg, recover above 68 mmHg, hold perfectly STEADY in between (62-68 mmHg). That "steady" band is exactly the septic clinical target zone (65±`TARGET_DEADBAND`=3) that `expert_controller.py` holds MAP in once treatment succeeds - so a **successfully treated** patient got SpO2 permanently frozen at whatever value it held when it entered that band, only ever resuming recovery if MAP later drifted above 68 via the separate, much slower illness-recovery mechanism. Reproduced directly: a test patient held at MAP=65.0-67.9 mmHg for 900+ simulated seconds had SpO2 frozen at 87.73% the entire time. Fixed by collapsing the 3-way split back to a 2-way one - reaching or exceeding the perfusion threshold (keeping a deadband only on the lower/decline side, to avoid noise-flicker right at that one remaining boundary) now starts recovery immediately. Re-verified on the same patient: SpO2 reaches 100% within seconds of crossing into target instead of freezing. `physiology.py`'s `update_spo2` is shared by both clinical modes, but the hypertensive side's dataset was not regenerated for this fix - hypertensive patients rarely linger in the narrow 62-68 mmHg band (they present far above it) per that engine's own code comments, so the practical effect there is negligible.

Items 28-30 together prompted three full dataset-regeneration-and-retrain cycles in about 24 hours (Part 7.3/8.1 carries only the final numbers) - worth mentioning in a Methodology "verification and validation" subsection as a concrete illustration of why re-running the full pipeline after every physiology change, rather than assuming a fix is isolated, matters: each of items 29 and 30 changed a physiological signal (`MeasuredHR`, `MeasuredSpO2`) that is a direct input feature to all three AI models, so leaving stale training data in place after fixing the underlying simulation would have left the deployed models trained on bugged data even after the bug was "fixed."

31. **Overstated "two orders of magnitude" PK-speed claim, found and corrected 2026-10-04**: `nitroprusside_pharmacokinetics.py`'s own module docstring (and this document's Part 4.3) claimed SNP's `ke` was "roughly two orders of magnitude larger" than norepinephrine's, offered as the reason the one-compartment PK model alone reproduces SNP's near-instant onset/offset vs. NE's slower one - a real, important claim for the "variable time-delay per drug" story a reviewer might ask about, but one that had never actually been checked against this simulation's own numbers. Checked directly: simulating both twins and computing `ke = clearance_l_min / vd_l` for representative patients gives `ke_NE≈0.14-0.21/min` and `ke_SNP≈0.25-0.47/min` - a real but modest ~1.7-2.7x difference, not 100x. Measuring the actual onset behavior (time from a cold start, flow=0, to 90% of eventual steady-state drug effect, across 3 different patients per drug) confirmed the *qualitative* claim is still correct - SNP reaches 90% effect in ~5 minutes vs. NE's ~11-13 minutes, and both lags are genuinely patient-variable (driven by each patient's own sampled clearance) - but the specific "two orders of magnitude" figure was simply wrong and has been corrected in both the code comment and this document. A good example of the same discipline already applied to citations this project (Part 2) - a confident-sounding quantitative claim in a comment is not verified just because it sounds physiologically plausible; it needs to be checked against what the code actually computes.

32. **Full citation-audit pass, 2026-10-05**, prompted by a 10-item checklist from a separate reviewing session.
